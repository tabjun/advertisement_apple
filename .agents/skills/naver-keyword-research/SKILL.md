# 네이버 키워드 리서치 (사과 스마트스토어)

목표: 감으로 키워드를 고르지 않는다. **검색량(수요) × 구매의도 × 경쟁강도 × 시즌**으로
키워드마다 점수를 매겨, 상품명·태그·검색광고에 넣을 후보를 근거와 함께 남긴다.
README의 분석 축 ①(Seasonality)·②(Driver)와 같은 데이터를 쓰므로 결과를 재사용한다.

먼저 실제 판매 상품의 품종·산지·등급/흠과 여부·중량/과수·수확/저장 상태·재고·배송 가능일을 확인한다.
판매하지 않는 품종·산지를 인기 있다는 이유로 추천하지 않는다. 현재 상품과 맞지 않는 수요는 별도의 상품 기회로 표시한다.
검색량만 큰 후보보다 **실제 구매로 이어질 가능성과 주문당 이익**을 우선한다. 미확인 상품정보는 질문으로 남긴다.

## 1. 데이터 소스 (각각 무엇을 알려주는가)

| 소스 | 얻는 값 | 주의 |
| :--- | :--- | :--- |
| 데이터랩 검색어트렌드 (`/v1/datalab/search`) | 기간 내 **상대지수 0-100**(일/주/월) | 요청 단위로 최댓값=100 정규화 → 요청이 다르면 수치 직접 비교 불가. 비교할 키워드는 **한 요청에 같이** 넣는다 |
| 데이터랩 쇼핑인사이트 (`/v1/datalab/shopping/...`) | 쇼핑 카테고리·키워드별 클릭 상대지수, 기기·성별·연령 분포 | 역시 상대지수. 카테고리 코드(농산물>과일>사과) 먼저 확인 |
| 검색광고 키워드도구 (SearchAd API `/keywordstool`) | 월간 PC/모바일 검색수、월평균 클릭수、경쟁정도、연관 키워드 | 통합검색 범위·집계기간을 확인. 쇼핑 구매 수요와 같지 않다. 경쟁정도는 광고 지표이며 자연검색 난이도가 아니다. `< 10`은 구간으로 보존하고 정확한 0·10으로 대체하지 않는다 |
| 쇼핑 검색 API (`/v1/search/shop.json`) | 검색 결과 수(total), 상품명·최저가·판매처·카테고리 | total은 고유 경쟁 판매자 수가 아니다. 정확도순 API 결과와 소비자 화면 순위를 동일시하지 않는다 |
| 스마트스토어 검색 리포트(Excel) | 우리 스토어에 실제 유입된 키워드 | 우선 수동 다운로드. 확보 가능한 열과 집계 범위를 확인하고 API 부재를 영구 전제로 두지 않는다 |

API 키는 `.env`에만 둔다(`.gitignore`에 포함됨). 키·원본 응답을 커밋하지 않는다.

## 2. 키워드 발굴 순서

1. **시드**: `사과`, 품종(`부사`, `홍로`, `시나노골드`, `감홍`, `아오리`), 산지(`청송사과`, `영주사과`, `충주사과` 등), 용도(`선물세트`, `못난이사과`, `가정용`), 규격(`5kg`, `10kg`, `소과`, `대과`).
2. **확장**: 키워드도구 연관 키워드 + 쇼핑 검색 상위 상품명에서 반복되는 토큰 + 우리 검색 리포트 유입 키워드.
3. **정제**: 동의어/띄어쓰기 변형은 하나의 그룹으로 묶되(예: `사과5kg`/`사과 5kg`) 검색량은 변형별로 따로 기록한다(네이버는 변형별 검색량이 다르다).
4. **분류**(각 키워드에 태그):
   - 의도: `구매형`(규격·가격·선물세트·산지직송) / `정보형`(효능·보관법·칼로리) / `탐색형`(품종명 단독)
   - 시즌: `상시` / `햇사과(8-11월)` / `명절(설·추석 D-30~D-1)` / `어버이날`
   - 범위: `빅키워드`(사과) / `미들` / `롱테일`(청송 부사 가정용 10kg)

## 3. 우선순위 점수

키워드별로 아래를 계산해 표로 남긴다. 가중치는 분석 단계에서 정하고 바꾸면 기록한다.

- 수요 `D` = 월간 검색수(PC+모바일) — 로그 스케일 권장
- 의도 `I` = 구매형 1.0 / 탐색형 0.5 / 정보형 0.2
- 경쟁 `C` = 검색 결과 수 ÷ 월간 검색수는 탐색용 대리지표로만 사용. 고유 판매자 수·자연검색 난이도·성공 확률로 해석하지 않는다. 비슷한 규격 상품의 가격·리뷰·배송 조건도 비교한다
- 시즌 적합 `S` = 지금(또는 광고 집행 예정 시점)이 그 키워드의 피크 구간인가 — 데이터랩 일별 추이로 판단
- 점수는 내부 정렬용 휴리스틱이다. 식·가중치·결측 처리·근거를 공개하고, 0·소량 검색수·중복 키워드 때문에 0 나눗셈/수요 중복 합산이 생기지 않게 한다. 자료가 없으면 수치 점수 대신 근거와 불확실성을 적는다

판단 규칙:
- 빅키워드와 미들·롱테일 모두 현재 검색 결과와 우리 유입을 보고 평가한다. 신규 스토어라는 이유만으로 불가능하다고 단정하지 않는다.
- 검색수가 높고 검색 결과 수가 적은 롱테일은 검토 후보일 뿐이다. 실제 상품 적합성·구매 의도·재고·총결제금액·주문당 이익을 확인해 우선순위를 확정한다.
- 정보형 키워드는 상품명에 억지로 넣지 않는다(적합도 하락) → 상세페이지 본문·블로그 콘텐츠 후보로 분리.

## 4. 산출물 형식

`result/`(gitignore 대상) 또는 분석 노트북에 아래 열로 저장하고, 결론만 `history.md`에 요약한다.

`keyword | group | intent | season | monthly_pc | monthly_mobile | comp_idx | shop_total | score | 사용처(상품명/태그/광고/콘텐츠) | 근거`

여기에 `대상 상품ID | 상품 일치 여부 | 출처/조회일/조건 | 주문당 이익(미확인 가능) | 불확실성 | 검증할 지표`를 추가한다.
검색광고 키워드도구의 후보를 쇼핑검색광고에 직접 입찰할 수 있는 키워드로 간주하지 않는다. 광고 유형별 타기팅·제외 설정은 최신 공식 도움말로 확인한다.

공식 해석 기준(2026-10-18 확인): [데이터랩 검색어트렌드](https://developers.naver.com/docs/serviceapi/datalab/search/search.md), [쇼핑 검색 API](https://developers.naver.com/docs/serviceapi/search/shopping/shopping.md). API 개발은 Excel 기반 1차 검토 후 필요할 때 한다.

## 5. 하지 말 것

- 상대지수(데이터랩)를 절대 검색량처럼 서로 다른 요청끼리 비교하지 않는다.
- 하루짜리 급등만 보고 시즌 키워드로 분류하지 않는다 — 급등 원인은 README 분석 축 ③(Anomaly)으로 넘긴다.
- 타 브랜드명·관련 없는 인기 키워드를 후보에 넣지 않는다(어뷰징으로 판정될 수 있음).
